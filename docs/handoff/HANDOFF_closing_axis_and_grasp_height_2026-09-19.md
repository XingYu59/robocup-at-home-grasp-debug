## §3 朝向（合拢轴）：这是"合到指令间距却空合"的最可能根因

### 3.1 合拢轴是**算出来的**，不是量出来的

`turtlebot3_manipulation_grasp/src/grasp_node.cpp:408`

```cpp
box_center.orientation = yawOnlyQuat(-robot_yaw_map_ + object_yaw_map_);
```

- `object_yaw_map_` = 配置常数（本世界物体都按出厂姿态摆 ⇒ 0）
- `robot_yaw_map_` = TF `map←base_footprint` 的偏航（= AMCL 的偏航）

⇒ 箱体的朝向（进而 MTC 的合拢方向）**完全挂在 AMCL 的偏航上**；
而驱动层命令的站位 yaw 是**桌沿法线**（来自地图、轴对齐 ✓）。两者不一致就没人发现 ✗

### 3.2 长方体对合拢轴的偏角极其敏感（新加的判据式子）

合拢轴与窄边夹角 φ 时，两指要张开的尺寸 =

```
span(φ) = depth·|cos φ| + width·|sin φ|        （HANDOFF_harness: closing_span_mm）
```

| 物体 | φ=0 | 10° | 15° | **19.8°** | 25.7° |
|---|---|---|---|---|---|
| potted_meat_can 50×97 | 50.0 | 66.1 | 73.4 | **80.2 = 开口上限** | 87.1 ✗ |
| cracker_box 60×158 | 60.0 | 86.5 ✗ | — | — | — |

⇒ **φ > 19.8° 时这只夹爪（开口 80 mm）在几何上就跨不进去**：两指会先压在物体顶面，
把物体推走，然后"合到指令间距而两指之间是空的" ✓ —— 与 §1 的 `[empty]` 完全吻合。

### 3.3 现场那一次的 φ

- 站位是**命令**"车头正对桌沿"的：`站位 = (2.193, 2.608, yaw=-1.571)`，法线 `(0,+1)`
  ⇒ 期望的箱体偏航（物体与 map 轴对齐）= **90°**
- 日志里 C++ 实际用的箱体偏航 = **115.7°** ⇒ **φ ≈ 25.7° > 19.8°** ✗

两种解释都指向同一件事（**必须查清再抓**）：

1. **车真没转到命令 yaw**（Nav2 余差 + 微调旋转）：那么合拢轴相对物体真的偏了 φ，
   抓取几何上不成立 ✗ —— 修法是抓之前把车头摆正并复核；
2. **AMCL 的偏航错了**（车其实正对桌沿，但 TF 报的 map 偏航偏了 25.7°）：
   那么规划里的箱体被整体转错 ⇒ 后果一样 ✗ —— 修法是让朝向不依赖 AMCL
   （从视觉/激光量物体的面法线、或量车相对桌沿的偏航）。

> 注意：**位置**不受这个偏航影响（视觉在 base 里量到物体、驱动再用同一个 TF 换算回去，误差抵消 ✓
> 这也正是"落点核对 0 mm"却夹空能同时成立的原因）。

## §8 P1 落地：桌腿基准 + 偏航补偿（2026-09-19）

### 8.1 为什么必须"量"而不是"修车"

合拢轴 = `box_yaw = object_yaw_map(常数) − robot_yaw_map(TF/AMCL)`。
AMCL 的偏航误差 e 是**常量偏置**：车一转，belief 跟着转 ⇒ **e 不变** ⇒
"把车头摆正"永远消不掉它 ✗（这也是为什么 §3.3 的两种解释都必须先量出来）。
⇒ 唯一出路：拿一条**不依赖 AMCL** 的基准把 e 量出来，再在算式里抵消掉。

### 8.2 基准 = 餐桌的 4 条腿（世界文件真值）

- `example.world` 的 `dinning_table_3`：桌面 0.5×1.2、4 条 0.03×0.03 的腿位于桌子局部
  (±0.235, ±0.585) ⇒ map 里就是 **(2.115/3.285, 1.765/2.235)**（脚本已逐条核对 ✓）；
- 激光（`/scan`，base_scan，z≈0.18 m，360 线、1° 一格、σ=10 mm）从桌沿外**看得见这 4 条腿**
  （桌面在 0.765，挡住的是桌面以上的视线，不挡腿 ✓）；
- 4 条腿在 base 里的半径 ≈ **0.38 / 0.85 / 1.12 / 1.38 m**（彼此差 ≥0.27 m）
  ⇒ **按半径匹配**（半径只跟车的**位置**有关、对偏航不敏感 ✓），再配一个 ±35° 方位窗防串台；
- 匹配到的 4 个点做 **2D Kabsch 闭式解**（纯 math）⇒ 车的 map 位姿 ⇒
  **e = TF 报的偏航 − 桌腿反解的偏航** ✓

> ★ 踩过的坑（离线自测直接抓到）：第一版按"预测位置附近 0.22 m"匹配 ⇒ belief 偏航一偏 25.7°，
> 0.9 m 处那条腿的预测位置就偏 0.39 m ⇒ **4 条腿只对上 1 条**，反解直接失败 ✗。
> 改成"半径匹配 + 方位窗"后：e=+25.7° 时 4 条腿全命中，偏航还原误差 **0.07°** ✓

### 8.3 怎么补偿（不动服务接口）

C++ 里 `box_yaw = object_yaw_map − robot_yaw_map`，真值应是 `0 − 真实偏航`。
真实偏航 = `robot_yaw_map − e` ⇒ 只要令 **`object_yaw_map := e`** 就自动抵消 ✓。
落地方式：

| 侧 | 改动 |
|---|---|
| 驱动 `grasp_phase.py` | `/scan` 订阅；`table_legs_map()` / `legs_from_scan()` / `fit_pose_from_landmarks()`（纯函数）；`_table_yaw_probe()` 量 e；`_apply_table_yaw_fix()` 在**每次抓之前**注入；`_inject_object_yaw()` 用 `/grasp_node/set_parameters` 写 `object_yaw_map` |
| C++ `grasp_node.cpp` | `toRequest()` 开头**每个请求重读** `object_yaw_map`（原来只在启动时读一次 ⇒ 注入不生效 ✗），改写时打一条 WARN ✓ |
| 诊断 | `★ 合拢轴核对` 现在同时给 **原始 φ / 已注入 e / 生效 φ**，并只用【生效 φ】判"夹不夹得进去" ✓ |

护栏（量不准就保持原行为，绝不乱改参数）：命中 <3 条腿、拟合残差 >20 mm、|e| >34°、
位置差 >0.5 m、`/scan` 缺失或过期、`set_parameters` 不可用 ⇒ 一律不注入并打 WARN ✓
|e| < 2° 时**显式写回 0**（防止上一趟注入的值残留到这一趟 ✗）。

## §9 追加：抓取前"一个目标都识别不出来"的真因（2026-09-19 10:25 那一趟）

**根因（视觉节点的模式判据写漏了调用方的请求）**：

```python
# 旧（problem）：只问"默认 4 类词表里有没有可夹的东西"，完全不管调用方点了哪几类

```

⇒ 只要画面里出现**任何**可夹的东西（本桌的 coke can、隔壁桌的 apple…）就永远不切"抓取模式"
（= 闭集复核，能命名 objects.yaml 的 18 类）⇒ 调用方点的类**永远没机会被命名** ✗✗

**修法**（`detect_grasp_target_node.py`，抽成可离线测的纯函数）：

```python
def needs_grasp_mode(found, want_pre, graspable, mode="auto"):
    want = list(want_pre) if want_pre else list(graspable)   # ★ 调用方点了类就按它判
    return not any(c in want for c in found)
```
