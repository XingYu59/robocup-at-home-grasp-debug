# 抓取编排设计（接进 patrol_task 的最终形态）

> 结论先行：**抓取不是单独跑一个节点，而是 patrol_task 的第二阶段**。
> 规则书 3.1：「拔高题不与基础题分开测试。参赛队伍可在完成基础题后，无须返回起点，
> 直接从客厅继续导航前往餐厅。」→ 一个进程、一次进场、两段任务。
> 本文件给出编排结构、代码组织、插入点、精度/时序约束与失败退路。

---

## 1. 三层职责（谁决定什么）

```
┌─ 编排层（patrol_task.py / dining_grasp_task.py）
│    · 导航到哪（观察点 / 餐桌站位）、什么时候调谁、失败了怎么办
│    · 选哪个目标（从视觉给的 targets[] 里挑一个可夹的）
│    · 底盘微调（相对闭环 creep）
│         ↓ 服务：/detect_grasp_target            （视觉侧给"物体在哪"）
│         ↓ 服务：/grasp_fixed_object             （把目标交给抓取侧）
├─ 适配层（grasp_node.cpp）
│    · 校验：新鲜度 / class_id 查表 / 支撑面 / 可达性
│    · 建规划场景：桌面 + 目标 + obstacles[]
│         ↓ 函数调用（同进程）
└─ 规划层（pick_and_place.cpp，MTC）：抓取阶段图 + 执行
```

编排层**不碰**像素、深度、碰撞箱、规划参数；适配层不碰"去哪个桌子、抓哪个"。
这条界线就是那三份 srv/msg 冻结契约的意义 ✓

## 2. 两段式流程（一个进程内）

```
Phase 0  等待 Nav2 → 发布 /initialpose → 等 AMCL 收敛
Phase 1（基础题，8 分钟预算）
   for 观察点 in [table_3, table_1, table_0, table_2]:
       NavigateToPose(观察点)              失败 → 打印 + 跳过（不阻塞）
       到点后 detect+计数 → Marker → 累计
   全部完成 → 打印三类名称+数量 → 写 <GROUP_NUMBER>_answer.json     ← 评分依据先落袋 ✓
Phase 2（拔高题）
   a. NavigateToPose(餐厅观察位, 距桌 ~1.0 m, 面朝餐桌长边)
   b. /detect_grasp_target {class_ids: [可夹类别...]}     ← 视觉给 targets[]（降序）
   c. 选目标：targets 里第一个「可夹 + 在可达范围内」的；其余当 obstacles
   d. 由目标的【map 位置】算出抓取站位（物体正前方 0.33 m，且离桌沿 ≥0.26 m）
      NavigateToPose(站位)
   e. creep 相对闭环：用【视觉给的相对量】把物体开到 base_footprint(0.33, 0)
   f. /grasp_fixed_object {target, obstacles}             失败按 stage 决定：
        BAD_TARGET / NO_SOLUTION → 换 targets 里的下一个（最多 N 次）
        SCENE_FAILED / EXEC_FAILED → 报错收尾（不重试，避免超时）
   g. 收尾：打印结果、结束
```

为什么 Phase 2 要"先观察位、再站位"：
观察位（~1.0 m）能看到**整张桌子**（选目标 + 拿其余物体当障碍），
站位（0.33 m）是为了机械臂够得着。两者之间的位移用里程计/TF 跟踪，
到站位后再用一次视觉（或里程计增量）闭环 → 见 §4 的精度要求。

## 3. 代码怎么组织（关键：**一份实现，两个入口**）

现在有两份"驱动"：`dining_grasp_task.py`（旧工作区的独立调试入口）与 `patrol_task.py`（比赛主流程）。
**不要把抓取逻辑复制进 patrol_task** ✗ —— 抽成模块：

```
turtlebot3_manipulation_navigation2/scripts/
├── patrol_task.py                # 比赛主流程：Phase 1 + 调 GraspPhase 跑 Phase 2
├── dining_grasp_task.py          # 独立调试入口：薄壳，只做参数解析 + 调 GraspPhase
└── grasp_phase.py（新增，建议）  # 抓取阶段的全部逻辑（导航站位/选目标/creep/调服务）
```

`GraspPhase` 复用什么、自己建什么：

| 需要的东西 | 来源 |
|---|---|
| 日志 / 时钟 / TF buffer | 传进来的 node（patrol_task 已经有 `_tf_buffer` ✓） |
| Nav2 action 客户端 | 复用 node 的 `nav_client`（patrol_task 已有 ✓）；没有就自己建 |
| `cmd_vel` 发布（creep 用） | 自己建（话题 `/cmd_vel`，launch 里 `cmd_vel_relay` 会转给底盘 ✓） |
| `/detect_grasp_target` 客户端 | 自己建（新增） |
| `/grasp_fixed_object` 客户端 | 自己建（已有） |
| 参数（站位余量、creep 容差、类别偏好…） | 走 node 的 ROS 参数，两个入口共用一套默认值 |

**插入点**（patrol_task.py 里最小改动）：`_navigate_next()` 走到最后一个观察点之后，
现在是调 `_all_done()` 就结束 → 改成 `_all_done()` 之后调 `self._grasp_phase.run()`，
并把 `main()` 里的单节点 spin 换成 `MultiThreadedExecutor`（grasp 阶段会在服务回调里等数据，
订阅回调要继续跑，否则死锁 —— 这个坑在视觉适配层里已经踩过一次 ✗）。

## 4. 精度约束（这是整个设计最硬的一条）

抓取是**指尖两点夹**（掌垫在指尖后方 11 mm，够不到 ≤0.08 m 的物体，见 `HANDOFF_grasp_objects_analysis.md`）。
合爪前手指开口 0.08 m，罐子宽 0.067 m → 物体中心必须落在夹爪中线 **±6.5 mm** 以内，
否则合爪时**从旁边合过去**（= 空夹）✗。

而现在的 creep 参数（`dining_grasp_task.py`）：

| 参数 | 现值 | 换算到横向误差（站位 0.33 m） | 是否够 |
|---|---|---|---|
| `CREEP_TOL = 0.02`（距离） | 20 mm | 沿视线方向 20 mm | 偏松 ⚠（靠视觉/真值的距离精度兜） |
| `CREEP_BEARING_TOL = 0.05`（方位 rad） | 0.05 rad | **横向 ±16.5 mm** | **太松 ✗**（比 6.5 mm 的窗口大一倍多） |

**建议**：`CREEP_BEARING_TOL` 收到 **0.012~0.015 rad**（横向 ±4~5 mm）、`CREEP_TOL` 收到 **0.005~0.008 m**；
并且 creep 环里的"物体相对位置"要用**同一把尺子**（全用视觉，或全用真值），别混 ✗。

顺带把视觉精度摊开（回答"相机高度影响多大"）：

| 物体形状 | 补偿方法的误差 | 说明 |
|---|---|---|
| 圆柱（coke can / tomato_soup_can / chips_can） | **≈0** | 相机水平看圆柱，可见面正好近一个半径，退回来精确落在轴心 ✓ |
| 球（apple） | ≈0.4 mm | 同理（半径 ≈ 窄边/2） |
| 方盒（cracker_box / sugar_box / mustard_bottle…） | **最坏几 cm** ⚠ | 盒子的可见面取决于它的**偏航角**：正对面时近半个窄边（补偿正确），角对着相机时近到"半个对角线"，误差 = (半对角线 − 半窄边)。实测算例：cracker_box 最坏 **54 mm**、sugar_box **29 mm**、mustard_bottle **27 mm** |

→ 所以：**接视觉抓圆柱类最稳**（罐头类）；要抓方盒，要么让编排层优先挑圆柱，
要么以后在适配层加"由掩码宽度剖面估物体偏航"的补偿。这一条与相机装的高度（0.80 m，
几乎与桌面 0.78 m 等高）直接相关：这个机位只能看到物体的**侧面**，看不到顶面，
所以"侧面近半个厚度"的假设必须成立 —— 对圆柱成立，对方盒不总成立。

可见性（按**相机到物体的实际距离 0.254 m** 算，站位 0.33 m 是底盘中心到轴心，相机在底盘前方 0.076 m）：

| 物体 | 底面仰角 | 顶面仰角 | 与垂直 FOV ±24.3° 比较 |
|---|---|---|---|
| coke can (0.124 高) | −6.5° | +20.5° | 整只可见 ✓（余量 ~4°）|
| apple (0.072) | −6.5° | +9.7° | 整只可见 ✓ |
| chips_can (0.25 高) | −6.5° | +41.0° | 顶部被切 ⚠ —— 但**不影响 xy 定位**（本方法只用点云的水平方向，z 直接取支撑面）✓ |

## 5. 失败与退化（比赛现场不能卡死）

| 情况 | 处理 |
|---|---|
| 观察点导航失败 | 打印 + 跳过（patrol_task 现在就是这样 ✓） |
| 视觉没结果 / 服务不可用 | 打警告 → Phase 2 直接跳过（基础题的分已经拿到），不要重试到超时 |
| 目标不可夹（bowl 之类） | 换 `targets[1]`；全都不行 → 报"没有可抓目标"收尾 |
| `stage=BAD_TARGET/NO_SOLUTION` | 换下一个目标重试（≤3 次），仍失败则收尾 |
| `stage=EXEC_FAILED` | 不重试（可能已把物体碰倒），打印后收尾 |
| 视觉目标"不新鲜"（>10 s） | 适配层每次检测都用当前时刻打戳 ✓；抓取侧仍会校验，拒收就重调一次服务 |

## 6. 与答案 JSON / 评分的关系

- Phase 1 结束时**立刻**写 `<GROUP_NUMBER>_answer.json`（`_save_answer_json()` 已有 ✓），
  再开始 Phase 2 —— 拔高题失败也不会影响基础题的提交 ✓
- 拔高题 30 分 = 导航到餐桌 10 + 桌面物品识别并框选标注 10 + 抓取抬起放回 10。
  其中"框选 + 文字标注"这一项要求**在仿真相机画面或等效可视化里框出拟抓取目标并标名称** ——
  现在视觉管线只往 RViz 打 Marker（`/detected_items`），**没有画到图像上** →
  建议 Phase 2 选完目标后，把那张图（框 + 类别文字）存盘（`SAVE_DEBUG_IMAGE` 已有类似机制）
  或发一个 Image 话题，作为"可核查"的证据 ✓（这条是评分项，别漏）

## 8. 实跑之后的三处修正（2026-09-13 夜）

### 8.1 观察位套用了可达性过滤（我的 bug）

`choose_target()` 原来无条件套"距臂基座 ∈ [0.10, 0.75]"。**观察位离桌 1.15 m，
桌上任何物体到臂基座都在 1.1~1.3 m** → 候选被全拒 → Phase 2 直接结束 ✗
（实测日志：`跳过 sugar_box：距臂基座 1.289 m 不在 [0.10, 0.75]`）
**改**：`choose_target(check_reach=...)` —— 观察位传 `False`，**只有站位上才查可达性** ✓

### 8.2 站位距离改成按"物体离桌沿多远"自适应

相机装在 z=0.80 m（桌面顶 0.795 m）、在车心前 0.076 m。物体**贴桌沿**时
（纵深 0.07，旧工作区验证过的情形）0.33 m 站位没问题 ✓；物体放在桌里侧 0.25 m 时，
0.33 m 站位会让**相机伸进桌面 7 mm** ✗ → gz 里相机撞桌板、creep 永远收敛不了 ✗

```
g = max(0.33, 沿接近方向走到桌沿的距离 + 0.08 + 0.05)
```
| 物体 | 走到桌沿 | 站位 g | 相机余量 | 臂基座距 |
|---|---|---|---|---|
| 贴桌沿的罐子 (3.0, 2.18) | 0.08 m | **0.33 m（旧几何不变 ✓）** | +0.17 m | 0.42 m ✓ |
| sugar_box (3.1, 2.00) | 0.26 m | **0.39 m** | +0.05 m | 0.48 m ✓ |
| 桌子正中 (2.7, 1.80) | 0.45 m | 0.58 m | +0.05 m | 0.67 m（接近上限 ⚠）|

> 注意：接近方向必须取【物体→机器人】的方位，**不能用"物体相对桌心的偏移"判断** ✗
> （实测：罐子在 (3.0,2.18) 时 |dx|=0.30 > |dy|=0.18，会误判成从 x 侧接近）

### 8.3 导航：根因是 `robot_radius` 不是膨胀半径

sim 用的 `turtlebot3_use_sim_time.yaml` 里 `robot_radius: 0.35`，而车体实际是
0.281×0.306 m（外接半径 ≈0.21）→ 致命带被放大 60%+ ✗。用地图做可达性统计（洪水填充）：

| robot_radius | 可通行面积 | table_3 观察点 | 抓取站位 (3.0,2.51) |
|---|---|---|---|
| 0.35（改前） | 43.5 m² | ✗ | **✗ 形式上都到不了** |
| **0.28（改后）** | **54.6 m²** | ✗（0.25 m 余量）| ✓（0.30 m 余量）|
| 0.25 | 60.2 m² | ✓ | ✓ |

**改**（两份 param 都改，install 里是符号链接 → 不用重新构建）：
`robot_radius 0.35 → 0.28`、`inflation_radius 0.55 → 0.45`、`cost_scaling_factor 3.0 → 4.0`
（致命区由 `robot_radius` 决定，`inflation_radius` 只是软避让衰减范围 → 降到 0.45 不损失安全性 ✓）

> `table_3` 观察点 (-4.70,-3.1) 离西墙只有 0.25 m：在严格的"≥robot_radius 才算安全"口径下
> 它是致命格；NavFn 对 inscribed(253) 格子的实际宽容度可能让它仍能规划 ✓。
> 若要彻底干净，把该点东移到 x ≥ -4.55（离墙 0.39 m）即可 —— **这条没动，等你定**。

## 9. 视觉驱动 creep：一次测量 + 里程计跟踪（2026-09-13 夜，第二版）

**问题**：适配层一次服务调用 = 默认路径 1 次检测 + 抓取模式 1 次 + 窄词表复核 1 次
≈ **12~15 s**。creep 若每轮都调视觉：18 轮 × 13 s = **234 s** ✗（预算 45 s ✗）

**正解（已实现）**：

```
站位上量【一次】物体位置 → 存成 odom 坐标（物体静止）
creep 每轮：用里程计把同一个 odom 点换算到当前 base_footprint → 10 Hz 闭环 ✓
creep 只走 0.2~0.6 m，里程计在这个尺度漂移几 mm ✓  全程不碰 gz 真值 ✓
```

几何验证（物体固定在 odom(3.1,2.0)，车沿实际轨迹走）：

| 车的位姿 | 换算出的 base 相对量 | 距离 |
|---|---|---|
| 观察位 (2.85, 3.05, −1.57) | (+1.050, +0.249) | 1.079 m |
| 站位 (2.82, 2.51, −1.18) | (+0.579, +0.062) | 0.583 m |
| creep 途中 (2.90, 2.30, −1.35) | (+0.337, +0.129) | 0.361 m |
| creep 到位 (2.95, 2.38, −1.40) | (+0.400, +0.083) | 0.409 m |

→ 连续、平滑，正是 creep 需要的反馈 ✓

**注意**：`_track` / `_final_map` / `_final_obs` 里存的都是 **odom 坐标**（不是 map ✗）——
map 那一段含 AMCL 误差（实测 0.16 m），掺进来会让抓取点偏 ✗

## 10. 实跑第三轮暴露的三个问题（2026-09-14）

### 10.1 ★根因：目标选到了**另一张桌子**上（车因此开上桌子）

日志：`② 抓取站位 = (2.849, 1.460)` —— `dinning_table_2` 脚印是 x2.1~3.3 / y1.25~1.75，
**站位正好落在桌子里面** ✗ → 导航目标点是致命格 → 车开上桌子（用户看到的"撞桌子"就是这个，
不是机械臂：FK 算出 **home 姿态指尖在车心前 0.215 m、高 0.963 m**，比桌面 0.795 高 17 cm ✓）

为什么会选到 table_2：观察位 (2.7,3.2) 面朝 −y，相机水平视野 62°，**前后两张桌子都在画面里**
（table_3 y1.75~2.25 近、table_2 y1.25~1.75 远）✗；抓取模式的标签又会错（把东西报成
cracker_box 0.73 / tomato_soup_can 0.50 ✗）→ 选中的目标在 map(2.836, 1.131) = table_2 一带 ✗

**修**：`choose_target()` 增加**支撑面校验** —— 目标必须落在 `dinning_table_3` 脚印内
（容差 0.20 m：既要吸收 AMCL 误差 ~0.16 m，又不能放进 table_2 上 y=1.5 的物体 ✗）
实测：table_3 的 sugar_box/bowl ✓ 通过；table_2 的 cracker_box(2.3,1.5) 与日志里那个
(2.836,1.131) ✗ 被挡掉 ✓

### 10.2 creep 跑了 152 轮

同一根因：车被桌子顶住 → 命令发出去不动 ✗。除了 10.1 的修复，另加**卡死早退**：

### 10.3 多帧投票（用户要求，已实现）

适配层 `vote_frames`（默认 3）：连续 N 帧各检一次，某类别要在 **≥⌈2N/3⌉ 帧**出现才采纳，
置信度取**中位数** ✓（假阳性逐帧随机、真目标稳定出现 → 投票近似除根）
抓取模式再叠一层**窄词表复核**（用投票选出的候选类做一次短 prompt 检测）✓

实测（参考图，3 帧）：

| 图 | 投票后 | 窄词表复核后 |
|---|---|---|
| `sugar_box` | `sugar_box` 0.42 / `tuna_fish_can` 0.32 | **`sugar_box` 0.85** ✓ / 0.52 |
| `mustard_bottle` | `mustard_bottle` 0.50 / `tuna_fish_can` 0.34 | **`mustard_bottle` 0.82** ✓ / 0.43 |

正确类稳定领先 0.33~0.39 ✓（编排层按档位+置信度排序，能选对 ✓）
